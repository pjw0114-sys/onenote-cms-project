# ROADMAP: 개인 개발 블로그 (OneNote CMS)

> 이 문서는 [`docs/PRD.md`](./PRD.md)를 기반으로 작성되었다. 실제 구현 시 `next@^16.2.11`, `react@^19.2.4`, `tailwindcss@^4`, `zod@^4` 등 최신 메이저 버전 기준으로 진행하며, 새 API 사용 전 `/breaking-check`로 `node_modules/next/dist/docs/` 및 타입 선언을 확인한다 (`CLAUDE.md`, `AGENTS.md` 참고).

## 개발 순서 원칙

아래 순서를 반드시 지킨다. 이유는 각 단계마다 "왜 이 순서인가" 섹션에 명시하지만, 핵심 원칙은 다음과 같다.

1. **의존성 역전 방지**: 상위 단계(핵심 기능)가 하위 단계(공통 모듈, 프로젝트 골격)에 의존하므로, 하위 단계가 먼저 안정화되어야 상위 단계에서 재작업이 발생하지 않는다.
2. **위험 요소 조기 검증**: OneNote/Graph API 인증처럼 리스크가 큰 외부 연동은 핵심 기능 단계 초반에 배치해 실패 시 조기에 방향을 전환할 수 있게 한다.
3. **점진적 확장**: MVP 범위(PRD 7절)를 먼저 완성하고, 백로그 항목(검색 고도화, 페이지네이션, RSS 등)은 그 이후에 얹는다.

## Phase 1. 프로젝트 초기 설정 (골격 구축)

### 할 작업

- Microsoft Graph API 클라이언트 패키지 설치 (`@microsoft/microsoft-graph-client`, `@azure/msal-node` 등) 및 버전 호환성 확인
- `.env`/`.env.local`에 Azure AD 클라이언트 ID·시크릿·테넌트 ID 등 환경 변수 정의, `.env.example` 작성
- Azure AD 앱 등록 및 Microsoft Graph API 권한(`Notes.Read` 등) 부여
- OneNote에 블로그용 노트북/섹션 생성, 페이지 메타데이터 속성(Title/Category/Tags/Published/Status) 규칙 확정
- `src/lib`에 Graph API 클라이언트 초기화 모듈 스캐폴딩 (인증 토큰 발급/캐싱 구조만, 실제 조회 로직은 3단계에서 구현)
- `src/config/site.ts`에 블로그 메타데이터(사이트명, 설명, URL) 반영
- 라우트 골격 확인: `/`(홈), `/posts/[id]`(상세), `/categories/[category]`(카테고리) — 이미 존재하는 `(marketing)` 라우트 그룹 기준으로 배치

### 왜 이 순서인가

OneNote API 인증은 PRD 10절에서 가장 큰 리스크로 지목된 항목이다. 인증/권한 구조가 확정되지 않으면 이후 모든 데이터 조회 기능이 흔들리므로, 코드를 작성하기 전에 계정·권한·환경 변수 체계를 먼저 굳혀야 한다. 라우트 골격도 이 시점에 정해두어야 2단계 공통 컴포넌트가 어떤 페이지에 배치될지 명확해진다.

### 예상 소요 시간

**2~3일**

### 완료 기준

- [ ] Azure AD 앱에서 발급한 자격 증명으로 Graph API 인증 테스트(토큰 발급)에 성공
- [ ] OneNote 노트북/섹션에 Title/Category/Tags/Published/Status 속성을 가진 테스트 페이지가 최소 1개 존재
- [ ] `.env.example`이 저장소에 커밋되어 필요한 환경 변수 목록이 문서화됨
- [ ] `/`, `/posts/[id]`, `/categories/[category]` 라우트 파일이 생성되어 있고 빈 페이지라도 빌드/렌더링 오류 없음

## Phase 2. 공통 모듈/컴포넌트 개발

### 할 작업

- OneNote 페이지 응답을 블로그 도메인 타입으로 변환하는 매퍼/DTO 정의 (`Title`, `Category`, `Tags`, `Published`, `Status`, `Content`)
- `Status = 발행됨` 필터링 로직을 서버 사이드 공통 함수로 구현 (PRD 10절의 "비공개 정보 노출" 리스크 대응)
- 글 목록/카드 UI 컴포넌트 (`src/components/common/` — 예: `PostCard`, `PostList`) 개발
- 카테고리 뱃지/태그 UI 컴포넌트 개발
- OneNote 페이지 HTML 콘텐츠를 sanitize하고 블로그 디자인 시스템에 맞게 렌더링하는 공통 컴포넌트 개발
- TanStack Query 기반 데이터 페칭 훅(`src/hooks/`) 정의 — 캐싱/재검증(ISR) 전략 포함
- 로딩/에러/빈 상태 공통 컴포넌트(`EmptyState` 등 기존 컴포넌트 재사용) 연결
- 반응형 레이아웃 기본 그리드/브레이크포인트 규칙 정의

### 왜 이 순서인가

핵심 기능(글 목록, 상세, 카테고리 필터)은 모두 "OneNote 데이터를 안전하게 필터링하고, 동일한 카드/렌더링 컴포넌트로 표시"하는 동작을 공유한다. 이 공통 로직과 UI를 먼저 만들어두지 않으면 3단계에서 페이지마다 필터링/렌더링 코드가 중복되고, Status=초안 노출 방지 같은 보안 규칙이 페이지별로 흩어져 실수하기 쉽다. 공통 모듈을 먼저 굳히면 핵심 기능 구현은 "조합"만 하면 된다.

### 예상 소요 시간

**3~4일**

### 완료 기준

- [ ] OneNote 응답 → 도메인 타입 매퍼에 대해 `Status=초안` 페이지가 결과에서 제외됨을 확인
- [ ] `PostCard`, 카테고리 뱃지, 콘텐츠 렌더러 컴포넌트가 Storybook 없이도 임시 페이지에서 정상 렌더링됨
- [ ] 데이터 페칭 훅이 TanStack Query 캐시/재검증 옵션과 함께 동작
- [ ] 로딩/에러/빈 상태가 실제 컴포넌트로 표시됨 (콘솔 에러 없음)

## Phase 3. 핵심 기능 개발 (MVP)

### 할 작업

- 글 목록 페이지(`/`): Status=발행됨 필터 + Published 내림차순 정렬 + 2단계 카드 컴포넌트 연동
- 글 상세 페이지(`/posts/[id]`): 페이지 ID 기반 라우팅, OneNote 콘텐츠 렌더링, 메타데이터(제목/카테고리/태그/발행일) 표시
- 카테고리별 필터링 페이지(`/categories/[category]`): Category 속성 기준 목록 필터링
- 기본 반응형 스타일 적용 (Tailwind CSS + shadcn/ui, 모바일/태블릿/데스크톱)
- API 호출 제한(Rate Limit) 대응 캐싱/ISR 재검증 주기 설정

### 왜 이 순서인가

PRD 7절 MVP 범위에 정의된 항목이 이 단계에 해당한다. 1단계에서 인증과 골격, 2단계에서 공통 컴포넌트/데이터 로직을 마쳤으므로, 이 단계는 화면 3개(홈/상세/카테고리)를 조합하는 작업에 집중할 수 있다. 검색이나 다크모드 같은 부가 기능보다 먼저 배치하는 이유는, MVP가 없으면 이후 기능이 검증할 대상 자체가 없기 때문이다.

### 예상 소요 시간

**4~5일**

### 완료 기준

- [ ] 홈에서 OneNote의 실제 발행 글이 최신순으로 노출됨
- [ ] 글 상세 페이지에서 실제 OneNote 콘텐츠(이미지 포함)가 정상 렌더링됨
- [ ] 카테고리 클릭 시 해당 카테고리 글만 필터링되어 표시됨
- [ ] 모바일/태블릿/데스크톱 뷰포트에서 레이아웃 깨짐 없음
- [ ] OneNote에서 새 글을 발행 후 캐시/재검증 주기 이내에 블로그에 반영됨 (PRD 9절 성공 지표)

## Phase 4. 추가 기능 개발

### 할 작업

- 검색 기능: 제목/태그 기준 클라이언트 또는 서버 사이드 검색 구현 (PRD 3절 기능 4)
- MVP 이후 백로그 우선순위에 따라 선택 구현: 페이지네이션/무한스크롤, 다크모드(이미 `next-themes` 연동되어 있어 토글 UI만 필요), RSS 피드
- 검색/필터 결과에 대한 정확도 확인 (PRD 9절 성공 지표)

### 왜 이 순서인가

검색과 백로그 기능은 PRD 7절에서 "MVP 이후 고려 사항"으로 명시되어 있다. MVP의 핵심 조회/표시 흐름이 안정된 뒤에 추가해야, 검색 인덱싱이나 페이지네이션이 아직 확정되지 않은 데이터 구조 위에서 반복적으로 재작업되는 것을 피할 수 있다.

### 예상 소요 시간

**3~4일** (선택 항목 범위에 따라 조정)

### 완료 기준

- [ ] 검색창에 제목/태그 키워드 입력 시 관련 글만 결과로 노출됨
- [ ] (구현한 백로그 항목에 대해) 각 기능이 기존 목록/상세 페이지 동작을 깨지 않고 동작함

## Phase 5. 최적화 및 배포

### 할 작업

- 이미지 최적화 (`next/image` 적용 여부 확인, `/breaking-check`로 Next 16 이미지 API 변경 사항 검토)
- SEO 최적화: sitemap, OpenGraph 이미지 자동 생성 (백로그 항목)
- Graph API 호출 캐싱/재검증 전략 최종 튜닝 (Rate Limit 리스크 재확인)
- Lighthouse 등으로 성능/접근성 점검 및 개선
- Vercel 배포 설정 및 환경 변수(Azure AD 자격 증명) 프로덕션 환경 등록
- 프로덕션 빌드(`npm run build`) 및 `npm run lint` 통과 확인

### 왜 이 순서인가

최적화와 배포는 기능이 확정된 뒤에 수행해야 효과가 있다. 기능이 계속 바뀌는 상태에서 성능 튜닝이나 SEO 메타데이터를 먼저 다듬으면, 이후 기능 변경 때마다 재작업이 필요해 비효율적이다. 배포는 전체 기능과 최적화가 끝난 마지막 단계에 배치한다.

### 예상 소요 시간

**2~3일**

### 완료 기준

- [ ] `npm run build`, `npm run lint`가 오류 없이 통과
- [ ] Vercel 프로덕션 배포 URL에서 실제 OneNote 데이터가 정상 표시됨
- [ ] Lighthouse 성능/접근성 점수에 대해 팀(또는 개인) 기준치 충족
- [ ] 프로덕션 환경에서 Status=초안 페이지가 노출되지 않음을 최종 확인
